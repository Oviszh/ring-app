提交保存代码快照；标签给这份快照一个固定、容易查找的名字；推送分支和标签后，远端也保存这个基准。它不是“已正式上线”的发布标签。

## 后续建议

1. 每个需求从最新主线新建 `codex/功能名` 分支。多个 agent 同时开发时使用不同分支及独立 worktree，避免共同修改同一目录。
2. 每完成一个可用的小功能提交一次，写清具体改动。测试通过、检查差异和 UI 基准后，再通过 PR 合并到主线。
3. 每个已验收里程碑新增附注标签并单独推送；不要重新指向已有基准标签，也不要强推覆盖主线。
4. 后续可在 GitHub 配置主线保护、禁止强推，以及合并前必须通过的 CI 测试。本轮只保存版本，不修改远端仓库规则。

## 找回这个版本

查看代码差异：

```sh
git diff baseline/local-v1.0.1-20261025..HEAD -- miniprogram
```

需要运行旧版本时，先保存当前未提交改动，再从标签创建恢复分支：

```sh
git fetch origin --tags
git switch -c codex/recover-local-baseline baseline/local-v1.0.1-20261025
```

这会在恢复分支上打开基准版本，保留主线后续提交。若只想撤销主线上某次有问题的改动，应评估后用 `git revert <有问题的提交>` 创建反向提交，再测试和推送；涉及合并提交或多个相互依赖的改动时需要单独判断，避免直接 `reset --hard` 后强推。

Git 保存代码和纳入版本库的文档，不保存用户手机中的修行记录。后续新增登录和云同步时，需要保持数据兼容、做好迁移与备份；代码回退不等于数据恢复。

参考：[Git 标签](https://git-scm.com/book/en/v2/Git-Basics-Tagging)、[Git revert](https://git-scm.com/docs/git-revert)、[Git worktree](https://git-scm.com/docs/git-worktree)。
